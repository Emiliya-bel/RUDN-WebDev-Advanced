# Design: Исправление API удаления карточек

## Контекст
Клиент (в `client/src/api/cards.ts`) отправляет DELETE-запрос на `/api/cards/:id`. Прокси Vite перенаправляет этот запрос на сервер, отрезая `/api` (в итоге сервер получает `/cards/:id`). Сервер сейчас не имеет такого маршрута, поэтому отвечает 404 (HTML).

## Принятые решения и альтернативы

### 1. Как принимать ID карточки?
**Решение:** Использовать параметр пути `req.params.id` (маршрут `app.delete('/cards/:id')`). Это стандартный REST-подход, который уже ожидает клиент.
**Альтернатива:** Передавать ID в query-параметрах (`?id=123`). Это потребовало бы изменения клиента, что запрещено условиями тикета (критерий 6).

### 2. Какой статус-код возвращать при успешном удалении?
**Решение:** Возвращать **200 OK**. Это стандартный ответ, означающий, что запрос выполнен успешно. Клиент просто проверяет `response.ok`, поэтому 200 подходит идеально.
**Альтернатива:** 204 No Content. Тоже допустимо, но 200 проще для понимания и не требует дополнительных проверок на клиенте.

### 3. Как обрабатывать неизвестные маршруты и ошибки?
**Решение:** Добавить в `server/index.ts` в самом конце (после всех `app.get`, `app.post`, `app.delete`):
- Middleware для 404: `app.use((req, res) => res.status(404).json({ error: 'Not found' }))`.
- Middleware для 500: `app.use((err, req, res, next) => { ... res.status(500).json(...) })`. 
**Важно:** обработчик ошибок должен иметь **4 параметра** (err, req, res, next), иначе Express не распознает его как error-middleware.

## Изменения в коде
- В `server/index.ts`: добавить `app.use(express.json())` в начало (если еще нет), изменить роут `app.delete('/cards/:id')`, добавить два middleware в конец файла.
- В `server/services/cards.service.ts`: проверить, что функция `deleteCard` корректно удаляет по ID и возвращает boolean.
